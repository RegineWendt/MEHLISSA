# UX-6.4 Run and Campaign Control

## Purpose and boundary

UX-6.4 connects the graphical workbench to the already accepted MEHLISSA
scenario and campaign process APIs. It adds no simulation, campaign-design, or
validation semantics in JavaScript. The browser may start either the exact
currently validated FP9/lung candidate or the curated UX-4 collector-count
campaign. Both remain research-software workflows and are not validated for
clinical decisions.

## Researcher workflow

1. Configure a scenario and wait for the authoritative validation decision.
2. Select an individual scenario or the curated controlled campaign.
3. Inspect the complete run plan, including candidate hash or campaign design,
   run count, seeds, sweep, paired comparison, and output destination.
4. Supply a safe output label and explicitly confirm the exact plan.
5. Monitor the queued, executing, collecting, and terminal stage.
6. If necessary, request cancellation. The host terminates the child process
   and retains its input, bounded command output, and cancellation record.
7. Inspect retained manifests, logs, provenance, results, summaries, and tables
   from capability-protected artifact controls.

An output label is not an arbitrary path. The host creates
`workbench-runs/<label>-<unique-id>/` inside the repository. Existing output is
never reused or overwritten. `--runs <repository-relative-directory>` changes
that bounded root when the workbench starts.

## Accepted execution boundary

The host reconstructs and revalidates every scenario candidate immediately
before allocating a job. It then calls `MehlissaClient.run_scenario()`. Campaign
starts accept only `campaign.fp9-collector-count`, validate its versioned
manifest, and call `MehlissaClient.run_campaign()`. The C++ executable remains
authoritative for simulation and generated scientific artifacts.

The process client now accepts an optional local cancellation event. Without
one, its public behavior is unchanged. With one, the client terminates the
owned MEHLISSA child process and raises `MehlissaCancelledError`; it never
converts cancellation into a successful result.

## Local API

All operations require the ephemeral `X-MEHLISSA-Session` capability and the
existing loopback/Host checks.

| Operation | Meaning |
|---|---|
| `GET /api/run-plans` | Return the bounded output root and curated campaign design. |
| `GET /api/runs` | List in-memory jobs created by this host process. |
| `GET /api/run?id=<id>` | Return one versioned run record. |
| `POST /api/run/scenario` | Revalidate and start an explicitly confirmed candidate. |
| `POST /api/run/campaign` | Validate and start the explicitly confirmed six-run campaign. |
| `POST /api/run/cancel` | Request termination of a queued or running job. |
| `GET /api/run/artifact?id=<id>&name=<name>` | Read a server-allowlisted retained artifact. |

The run API version is `1.0.0`. Unknown job identifiers, artifact names,
campaigns, editable fields, and unsafe labels fail closed. Browser requests
cannot select arbitrary source or destination paths.

## Retained evidence and states

Every job has a `run-record.json`, an exact retained input, UTC timestamps,
kind, source or campaign identity, candidate hash where applicable, declared
run count, seeds, status, stage, progress, cancellation flag, error text,
bounded logs, and an allowlist of artifacts. Updates use an atomic replacement.

Terminal states are `completed`, `failed`, and `cancelled`. A failed or
cancelled job remains a job; it is not an observation and must not be included
as successful campaign data. The browser displays at most the last 200 lines
and 64,000 characters of command output. That same bounded text is retained as
`command-output.log`; scientific run logs generated by MEHLISSA remain separate
artifacts.

## Acceptance evidence

Local acceptance on 3 September 2026 covers:

- the reference FP9/lung scenario completing through `run_scenario`, with its
  exact input, result, provenance, simulation log, summary, command log, and
  workbench run record linked;
- the UX-4 campaign completing six derived runs through `run_campaign`, with
  the two declared replicates, collector-count sweep, paired comparison, seeds,
  result JSON, and CSV retained;
- an actual campaign cancellation reaching `cancelled` with the cancellation
  request and retained evidence recorded;
- rejection of an invalid scenario, missing confirmation, unsafe output label,
  unknown campaign/run/artifact, and path traversal;
- bounded log and repository-contained output behavior; and
- full Windows/MSVC tests plus desktop and narrow-viewport browser review.

Publication and supported GitHub CI remain pending an explicit push request.
UX-6.5 will read the accepted result artifacts and add a dashboard and
comparison workflow; it must not reinterpret missing, failed, or cancelled jobs
as observations.
